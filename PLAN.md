# План реалізації — анахронізм, дублікати, гомогліфи, техборг

Обсяг узгоджено з експертом: реалізуються **чотири** блоки. Онлайн-верифікація
джерел, цитати без посилань, стилометрія, прихований текст, метадані та
експорт звіту — **не входять** у цей етап.

Порядок робіт навмисно починається з техборгу: етап 0 — це саме той рефакторинг
кешування, у який потім вмикаються всі три нові перевірки. Якщо зробити його
після, `app.py` доведеться правити двічі.

| Етап | Зміст | Нові файли | Правки |
|---|---|---|---|
| 0 | Техборг + рефакторинг кешу | — | `app.py`, `extractor.py`, `highlighter.py` |
| 1 | Анахронізм | `parser/anomalies.py` | `year_extractor.py`, `types.py`, `app.py` |
| 2 | Дублікати за назвою | `parser/duplicates.py` | `app.py` |
| 3 | Гомогліфи | `parser/text_forensics.py` | `app.py` |

---

## Спільна інфраструктура

У `parser/types.py` додається один спільний enum — щоб усі три перевірки
говорили однією мовою, а UI малював їх однаково:

```python
class Severity(Enum):
    PROOF   = "proof"     # 🔴 технічно неможливо
    SUSPECT = "suspect"   # 🟡 аномалія, потрібен погляд людини
```

Рівня `UNKNOWN` тут немає — він був потрібен для онлайн-верифікації, яка в цей
етап не входить. Усі три перевірки працюють офлайн і завжди дають визначену
відповідь.

Кожен модуль повертає власний dataclass із полем `severity`. Спільного
`Finding` не робимо: у трьох перевірок надто різні набори полів, і узагальнення
дало б словник `details: dict`, який нічого не типізує.

## Етап 0 — техборг

### 0.1 `split_zones` виконується на кожному ререндері — головне гальмо

Це виявилось серйозніше, ніж записано в `ROADMAP.md`. `split_zones(lines)`
викликається в головному потоці `app.py` **поза будь-яким кешем**, тобто на
кожен клік по будь-якому віджету. Усередині `_select_biblio_header()` для
кожного кандидата-заголовка робить повний `parse_bibliography()` по хвосту
документа. Коли заголовок повторюється колонтитулом на 40 сторінках
бібліографії — це 40 повних парсингів хвоста **на кожне натискання кнопки**.

Правка одна — кешування в `app.py` за зразком наявного `cached_analyze`:

```python
@st.cache_data(show_spinner="Аналіз структури…")
def cached_split_zones(lines_tuple):
    return split_zones(tuple_to_lines(lines_tuple))
```

**Внутрішню оптимізацію `bibliography.py` не робимо.** Розглядався варіант
замінити `_zone_end()` (сканує документ уперед для кожного кандидата) на
попередній обрахунок стоп-позицій за один зворотний прохід. Перетворення
тотожне, але воно прибирає лише один доданок `O(k·n)` із двох: домінує
`parse_bibliography()` на кожного кандидата, і він лишається. Кеш знімає
проблему повторних запусків повністю, а правка зачіпає логіку під
`tests/test_biblio_selection.py` заради майже нульового виграшу.

Обмеження вікна оцінювання кандидатів **свідомо не робимо** з тієї ж причини:
обрізання вікна змінило б поведінку правила вкладеності.

### 0.2 Роки та ДСТУ рахуються заново на кожному ререндері

`extract_years()` і `validate_bibliography()` викликаються прямо в
`render_tab_checker` — на відміну від `cached_analyze`. Замість того щоб
загортати кожну окремо (їхній аргумент `dict` не хешується), розширюємо
`cached_analyze` до одного зібраного результату:

```python
@dataclass
class AnalysisBundle:
    bibliography: dict[int, str]
    citations: dict[int, str]
    result: dict
    years: dict[int, int | None]
    year_confidence: dict[int, str]       # етап 1
    dstu: dict[int, DstuStatus]
    duplicates: list[DuplicateGroup]      # етап 2
```

Один парсинг, один запис у кеші, усі похідні дані поруч. Сюди ж потім
під'єднуються дублікати (етап 2) — вони O(n²) і кеш їм потрібен.

Анахронізм у бандл **не входить**: він залежить від року дисертації, який
експерт може ввести вручну, тобто змінюється без зміни бібліографії. Він
дешевий (O(n)) і рахується поза кешем.

### 0.3 Дрібні правки

| Що | Де | Дія |
|---|---|---|
| Мертві параметри `file_bytes`, `filename` | `app.py`, `render_tab_checker` | Прибрати з сигнатури й з виклику |
| Мертвий запис `st.session_state["zone_result"]` | `app.py` | Прибрати — ніде не читається |
| Роздутий вихідний PDF | `highlighter.py` | `doc.tobytes(deflate=True, garbage=3)` |

Про `garbage=3`: він стискає невикористані об'єкти у **вихідному** файлі й
зменшує його розмір. Другу копію в пам'яті (відкритий `doc` плюс повернуті
байти) він не прибирає — це окрема задача, у цей етап не входить.

### 0.4 Рік дисертації через розрив рядка

`_ANCHOR_CITY_YEAR` вимагає місто й рік **в одному рядку**. На титульних
сторінках PDF «Київ» і «2023» майже завжди два окремі рядки, тож спрацьовує
запасний прохід `max()`, який може підхопити рік із УДК або з назви закону.

Через анахронізм ця похибка стає дорогою: неправильний рік дисертації дає
хибні звинувачення по всьому списку.

Список міст виноситься в спільну константу `_CITIES` (зараз він зашитий
всередині регулярного виразу [`extractor.py:232`](parser/extractor.py:232)).
Раз константа все одно виноситься — доповнюємо її містами, де реально
відбуваються захисти, а в наявному списку їх немає: **Острог, Умань,
Переяслав, Дрогобич, Кам'янець-Подільський, Слов'янськ, Біла Церква,
Маріуполь, Краматорськ**.

З константи будуються два патерни:

```python
_CITY_ONLY  = re.compile(rf'^\s*(?:{_CITIES})\s*[–—\-,]?\s*$', re.UNICODE)
_BARE_YEAR  = re.compile(r'^\s*(20[0-2]\d|19[89]\d)\s*(?:р(?:ік|\.)?)?\s*$')
```

Новий прохід 1а-біс, одразу після наявного 1а: рядок збігся з `_CITY_ONLY` →
дивимось рядки `i+1` та `i+2` на `_BARE_YEAR`. Решта проходів і їхній
пріоритет не змінюються.

**Тести:** доповнити `tests/test_extractor_meta.py` кейсом «місто і рік
різними рядками» і кейсом «між містом і роком порожній рядок».

## Етап 1 — анахронізм

### 1.1 Достовірність року видання

`extract_year()` перебирає чотири патерни. Перші три прив'язані до контексту
(`, 2019.` · `(2019)` · `, 2019` у кінці) — це справді поле року за ДСТУ.
Четвертий — загальний захват будь-якого числа, схожого на рік, будь-де в
записі. Він може взяти рік із назви («Закон України 2020 року про…»), а не рік
видання.

Для анахронізму ця різниця критична, тому `year_extractor.py` починає
повідомляти, звідки взято рік:

```python
def extract_year_with_confidence(entry: str) -> tuple[int | None, str]:
    """(рік, 'strong' | 'weak' | 'none') — 'weak' для загального патерну."""
```

`extract_year()` лишається тонкою обгорткою — наявні виклики й тести не
ламаються.

### 1.2 Модуль `parser/anomalies.py`

```python
@dataclass
class Anachronism:
    source_year: int
    delta: int                  # source_year - dissertation_year (0 якщо року немає)
    severity: Severity
    reason: str

def find_anachronisms(
    years: dict[int, int | None],
    confidence: dict[int, str],
    dissertation_year: int | None,
    current_year: int | None = None,
) -> dict[int, Anachronism]:
```

Поля `num` у dataclass немає навмисно — воно дублювало б ключ словника
`dict[int, Anachronism]`.

Правила застосовуються згори вниз, перше збіжне виграє:

| Умова | Рівень | Формулювання |
|---|---|---|
| `year > current_year` | 🔴 `PROOF` | «рік видання ще не настав» |
| `delta >= +2`, патерн `strong` | 🔴 `PROOF` | «джерело новіше за рік на титульній сторінці» |
| `delta == +1`, патерн `strong` | 🟡 `SUSPECT` | «джерело на рік новіше — можливо, рік подання проти року захисту» |
| `delta >= +1`, патерн `weak` | 🟡 `SUSPECT` | «рік видання визначено неточно — перевірте запис» |

**Правило «рік ще не настав» не залежить від року дисертації.** Воно
працює й тоді, коли `dissertation_year is None`: рік у майбутньому — це
знахідка сама по собі. Решта правил без `dissertation_year` не виконуються,
бо `delta` порахувати нема від чого.

`current_year is None` → перше правило пропускається, решта працюють.
`current_year` — параметр, а не `datetime.now()` усередині: інакше тест
доведеться прив'язувати до системного годинника.

**Чому `delta == +1` — це 🟡, а не 🔴.** Рік на титульній сторінці — це рік
подання, захист може бути наступного року, тож `delta = +1` регулярно
трапляється в цілком чесних роботах. Якби він давав 🔴 «технічно неможливо»,
червоний колір знецінився б на першій же нормальній дисертації. А `delta = +3`
артефактом оформлення бути не може.

**`delta` показується в UI обов'язково** — і для 🔴, і для 🟡. Показуючи
різницю, а не голий прапорець, ми даємо експертові відкалібрувати самому,
замість того щоб зашивати поріг у код і мовчки помилятися.

**Відома межа охоплення.** `_YEAR_PATTERNS` у
[`year_extractor.py:5`](parser/year_extractor.py:5) ловить роки лише до 2029
(`19[89]\d|20[0-2]\d`). Тому запис із роком 2045 не витягнеться взагалі —
`extract_year()` поверне `None`, і правило «рік ще не настав» промовчить.
Практично воно працює у вікні від поточного року до 2029. Розширювати регулярні
вирази **свідомо не будемо**: ширший патерн частіше чіплятиме числа з назв
(«Стратегія 2030») у фолбек-проході. Повернутися до цього треба до 2030 року,
інакше зламається й визначення року дисертації.

### 1.3 Ручне введення року дисертації

Обов'язковий супутник перевірки: якщо `extract_dissertation_year()` помилився
або повернув `None`, увесь блок або мовчить, або бреше.

У `app.py` поруч із блоком автора — `st.number_input` у `st.expander`
«📅 Рік дисертації», попередньо заповнений автоматично визначеним значенням.
Експерт бачить, що саме визначила програма, і може виправити. Введене значення
перекриває автоматичне.

### 1.4 Відображення — «окремо відмітити» на трьох рівнях

**а) Окрема секція, найперша після метрик.** Порядок секцій у вкладці
«Перевірка джерел» стає таким:

```
метрики → 🔴 Анахронізми → 🟡 Дублікати → ⚠️ Сироти
        → ✅ Використані → 👻 Фантомні → 📊 Роки → 📐 ДСТУ
```

Заголовок секції — «🔴 Джерела новіші за дисертацію», а не «Неможливі
джерела»: після рішення по §1.2 туди потрапляють і 🟡-знахідки, і назва
«неможливі» їх би обмовляла.

Анахронізм і дублікати йдуть **до** сиріт: сирота — це привід подивитися,
а джерело з майбутнього — знахідка.

Таблиця: `№` · `Рівень` · `Рік видання` · `Різниця` · `Запис`. Повний текст
запису обов'язковий — експерт має бачити підставу, а не вирок.

Колонка `Рівень` потрібна, бо після рішення по §1.2 секція змішана: у ній
живуть і 🔴 (`delta ≥ +2` або рік ще не настав), і 🟡 (`delta = +1`, або
`weak`-патерн). Сортування — 🔴 згори, всередині рівня за спаданням `delta`.
Рядки сортуються так, щоб найгірше було видно без прокручування.

**б) Метрика в шапці.** Рядок метрик умовно розширюється, і додаткові колонки
з'являються **тільки коли знахідки є** — щоб на чистій роботі не висів нуль,
який нема з чим співвіднести.

Умовних метрик буде дві: анахронізми (етап 1) і дублікати (етап 2), тож
жорсткий індекс `cols[3]` не годиться — якщо дублікати є, а анахронізмів
немає, він вилетить за межі. Метрики збираються в список і розкладаються
за фактичною довжиною:

```python
metrics = [
    ("Джерел у списку", total, None),
    ("Використовуються у тексті", used_count, f"{used_pct:.0f}%"),
    ("Не згадуються у тексті", orphan_count, ...),
]
if anachronisms:
    metrics.append(("🔴 Анахронізмів", len(anachronisms), None))
if duplicates:
    metrics.append(("🟡 Дублікатів", len(duplicates), None))

cols = st.columns(len(metrics))
for col, (label, value, delta) in zip(cols, metrics):
    col.metric(label, value, delta=delta)
```

Той самий список використовує й етап 2 — окремого правила для дублікатів
не заводимо.

**в) На графіку розподілу за роками.** Замість одного `go.Bar` — два трейси:
звичайні роки `#4f98a3`, анахронічні `#d13b3b`, з легендою. Пунктирна лінія
року дисертації лишається. Червоні стовпчики праворуч від лінії роблять
проблему видимою без читання таблиць.

### 1.5 Тести — `tests/test_anomalies.py`

Чисті функції над словниками, PyMuPDF не потрібен:

* джерело новіше за дисертацію на 2+ роки, патерн `strong` → `PROOF`;
* те саме з патерном `weak` → `SUSPECT`;
* `delta == +1`, патерн `strong` → `SUSPECT`, **не** `PROOF`;
* рік у майбутньому відносно `current_year` → `PROOF` навіть без року дисертації;
* `dissertation_year is None` і жодного року в майбутньому → порожній результат;
* `current_year is None` → правило «рік ще не настав» не спрацьовує, решта працюють;
* рік == рік дисертації → не знахідка (робота може цитувати видання свого року);
* `year is None` у частині джерел → пропускаються без помилки;
* `delta` рахується правильно;
* `extract_year_with_confidence` повертає `strong` для `«Київ, 2019. 320 с.»`
  і `weak` для року, що трапився лише в тілі назви.

## Етап 2 — дублікати за назвою

### 2.1 Виділення назви

Порівнювати цілі записи не можна: дві різні статті одного автора в одному
журналі за один рік дають дуже високу схожість рядків. Тому спершу
виділяємо поле назви за структурою ДСТУ 8302:2015.

```python
def extract_title(entry: str) -> tuple[str, str]:
    """(назва, метод) — метод: 'dstu' | 'full' (запасний варіант)."""
```

Алгоритм:

1. Зняти блок авторів на початку — `Прізвище І. І.`, повторно, поки знімається
   (авторів може бути кілька через кому). Підтримати `ПРІЗВИЩЕ І. І.` великими
   і латинський варіант `Surname A. B.`
2. Обрізати за першим із розділювачів ДСТУ: `' : '`, `' // '`, `' / '`, `' ; '`.
3. Обрізати за `'. '` перед великою літерою, якщо голова довша за 15 символів
   (ініціали вже знято на кроці 1, тож ризику розрізати `І. І.` немає).
4. Якщо залишилось менше 10 символів — сегментація не вдалася; повертаємо
   нормалізований повний запис і метод `'full'`.

**Записи з методом `'full'` беруть участь тільки в точному порівнянні.**
У near-порівняння (`SequenceMatcher >= 0.90`) вони не потрапляють — ні між
собою, ні з нормально сегментованими. Причина: у повному записі левову частку
рядка займають службові поля ДСТУ («// Вісник … . 2019. С. 12–18»), однакові
в усіх статтях одного журналу. Дві різні статті одного автора там дадуть
`ratio` під 0.9 на самій лише службовій частині — тобто рівно та хиба, заради
якої §2.1 і виділяє назву. Ціна рішення: дубль у двох підряд зіпсованих
записах ми пропустимо. Це прийнятно — хибне звинувачення дорожче.

Нормалізація назви: нижній регістр, зняття пунктуації, стиснення пробілів,
викидання стоп-слів (`та`, `і`, `в`, `у`, `на`, `для`, `з`, `до`, `the`, `of`,
`and`) і однолітерних токенів.

### 2.2 Порівняння

```python
@dataclass
class DuplicateGroup:
    numbers: list[int]
    kind: Literal["exact", "near", "same_title_diff_year"]
    similarity: float
    severity: Severity

def find_duplicates(
    bibliography: dict[int, str],
    years: dict[int, int | None],
    threshold: float = 0.90,
) -> list[DuplicateGroup]:
```

Пари й вердикти:

| Умова | `kind` | Рівень |
|---|---|---|
| Нормалізовані назви ідентичні, роки збігаються | `exact` | 🟡 `SUSPECT` |
| Нормалізовані назви ідентичні, роки різні | `same_title_diff_year` | 🟡 `SUSPECT` |
| `SequenceMatcher.ratio() >= 0.90`, **обидві назви методом `'dstu'`** | `near` | 🟡 `SUSPECT` |

`same_title_diff_year` виділено окремо навмисно: та сама праця, внесена двічі
зі зміненим роком, — це не недогляд оформлення, а спроба зробити дубль
несхожим на дубль.

Усе на рівні 🟡: дубль у списку може бути й помилкою оформлення (два видання
однієї монографії), тож останнє слово за експертом.

**Групування транзитивне** (union-find): якщо 12≈187 і 187≈45, це одна група
`[12, 45, 187]`, а не три пари.

**Передфільтр перед `SequenceMatcher`** — інакше O(n²) на 500 джерелах це
125 тис. викликів:

* відношення довжин < 0.7 → пропуск;
* Jaccard за множинами токенів < 0.4 → пропуск.

Прототип на реальних записах ДСТУ підтвердив пороги:

```
 12/ 45  jaccard=1.00  ratio=1.00  → точний дубль (авторський / за ред., різні роки)
 12/187  jaccard=1.00  ratio=1.00  → точний дубль
 88/ 90  jaccard=0.60  ratio=0.83  → НЕ дубль ✓ («цифрових платформ» / «цифрових ринків»)
```

Запас між 0.83 і порогом 0.90 достатній: дві близькі, але різні статті одного
автора не злипаються.

### 2.3 Відображення

Секція «🟡 Дублікати у списку» одразу після анахронізмів. Таблиця:
`Група` · `Номери` · `Схожість` · `Тип` · тексти всіх записів групи.
Метрика «🟡 Дублікатів» у шапці додається в той самий список `metrics` із
§1.4б — окремої логіки колонок не заводимо.

Додатковий рядок під таблицею — скільки позицій зі списку є повторами:
для нормативного мінімуму в 200 джерел це прямо стосується того, чи набрано
норму насправді.

### 2.4 Тести — `tests/test_duplicates.py`

* `extract_title` на чотирьох формах ДСТУ: автор-перший, назва-перша через `/`,
  стаття через `//`, стаття без `//`;
* `extract_title` на сміттєвому записі → метод `'full'`;
* точний дубль знаходиться;
* дубль із різними роками → `same_title_diff_year`;
* дві різні статті одного автора з близькими назвами → **не** дубль
  (кейс `88/90` як регресійний, з фіксацією `ratio ≈ 0.83`);
* транзитивна група з трьох;
* порожній і однозаписний список → порожній результат;
* передфільтр не викидає справжній дубль із різною довжиною запису;
* **два сміттєві записи (обидва метод `'full'`) із `ratio >= 0.90` → не дубль**;
* два ідентичні сміттєві записи (метод `'full'`, збіг точний) → дубль знаходиться.

## Етап 3 — гомогліфи

### 3.1 Таблиця підмін

Кодпоінти звірено з `unicodedata`. Для української найважливіші —
`і` U+0456 ↔ `i` U+0069 та `І` U+0406 ↔ `I` U+0049: буква `і` в українському
тексті одна з найчастіших, а `і` — ще й сполучник, тобто окреме слово.

| Нижній регістр | Верхній регістр |
|---|---|
| `а`↔`a` · `е`↔`e` · `і`↔`i` · `о`↔`o` · `р`↔`p` | `А`↔`A` · `В`↔`B` · `Е`↔`E` · `І`↔`I` · `К`↔`K` |
| `с`↔`c` · `у`↔`y` · `х`↔`x` · `ї`↔`ï` | `М`↔`M` · `Н`↔`H` · `О`↔`O` · `Р`↔`P` · `С`↔`C` |
| `ј`↔`j` · `ѕ`↔`s` | `Т`↔`T` · `У`↔`Y` · `Х`↔`X` · `Ї`↔`Ï` · `Ј`↔`J` · `Ѕ`↔`S` |

Грецькі двійники (`ο` `α` `ρ` `ν` `Α` `Β` `Ε` `Ι` `Κ` `Μ` `Ν` `Ο` `Ρ` `Τ` `Χ`)
додаються в ту саму таблицю: трапляються рідше, коштують нуль.

### 3.2 Правила виявлення

**Ключова передумова — розбиття токена по дефісах і апострофах перед
аналізом.** Саме воно знімає майже всі хибні спрацювання: `IT-технології`
розпадається на `IT` (суцільна латиниця) і `технології` (суцільна кирилиця),
жодне з них не змішане. Так само `e-mail`, `COVID-19`, `Web-сайт`.

**H1 — змішане слово.** Підтокен містить літери двох систем письма, кирилиця
становить ≥ 50 % літер, і **всі** латинські літери є гомогліфами. Рівень
🔴 `PROOF`: випадково набрати кириличне слово з латинською `i` всередині
неможливо — розкладка так не перемикається.

**Зворотний напрямок — кирилиця всередині латинського слова — не робимо.**
Симетричне правило знадобилося б для англомовної анотації, але це 2–3 сторінки
проти двохсот, а коду й тестів воно подвоює. Якщо повернемось — узагальнити
H1 до «домінуюча система письма ≥ 50 %, усі літери іншої системи є
гомогліфами», решта правила не змінюється.

**H2 — самотня латинська літера-слово.** Окремий токен з однієї латинської
літери між двома кириличними словами. Це та сама підміна `і → i`, але слово
з однієї літери на 100 % латинське, тож правило H1 його пропускає — потрібне
окреме.

Розділяється за впевненістю:

* `i`, `ï` — 🔴 `PROOF` завжди. Латинські `i`/`ï` окремим словом в
  українському тексті не трапляються, а `і`/`ї` — сполучник і прийменник.
* `y`, `o`, `a`, `e` — спрацьовують **тільки якщо H1 уже дало ≥ 3 знахідки**,
  тобто підміну в документі вже доведено. Поза цим контекстом вони дають
  хибні спрацювання на змінних і латинських вставках.
* `x`, `c`, `p` — виключені повністю: це надто поширені математичні змінні.

Додаткові запобіжники для H2: літера в нижньому регістрі; за нею не йде
`)`, `.`, `=`, `,` (відсікає переліки «a) b)» і рівняння).

### 3.3 Перевірка правил на пастках

Прототип прогнано на реальних формулюваннях, включно з тими, що мають
спрацювати хибно:

```
[чистий текст]                     0 знахідок ✓
[підміна в словах]                 2 — «Адмiнiстративна», «вiдповiдальнiсть» ✓
[самотня латинська i]              1 — «i» → «і» ✓
[IT-технології / e-mail / COVID]   0 ✓  (розбиття по дефісу)
[перелік «a) b)»]                  0 ✓  (запобіжник на дужку)
[латинська цитата pacta sunt]      0 ✓  (суцільна латиниця, не змішана)
[ЗАГОЛОВОК ВЕЛИКИМИ]               3 — «РОЗДIЛ», «ТЕОРЕТИЧНI», «УПРАВЛIННЯ» ✓
```

Єдине хибне спрацювання прототипу — `x` у «Нехай x дорівнює 5» — знято
виключенням `x`, `c`, `p` із набору H2.

### 3.4 Розрізнення атаки й поламаного шрифту

Найнебезпечніший сценарій хибного звинувачення: PDF із пошкодженою мапою
`ToUnicode` віддає латинські гліфи замість кириличних по **всьому** документу.
Виглядає як тотальна підміна, насправді — дефект конвертера.

Дискримінатор — розподіл, а не кількість:

* підміни рівномірно розмазані по всіх сторінках і майже в кожному слові
  (> 5 % слів **і** уражено > 80 % сторінок) → `likely_encoding_issue = True`,
  показуємо як «ймовірна проблема кодування шрифту», а **не** як підміну;
* підміни зібрані в окремих абзацах чи на окремих сторінках → підміна.

Реальна атака точкова за визначенням: підмінюють тільки те, що інакше знайде
пошук збігів.

**DOCX: другий критерій відпадає.** У DOCX номерів сторінок немає — `page`
дорівнює `None` в усіх рядках, і UI це вже визнає прямо
([`app.py:212`](app.py:212)). Тому для DOCX `likely_encoding_issue` рахується
**тільки за часткою уражених слів** (> 5 %), без умови про сторінки.
`pages_affected` лишається порожнім списком, колонка «Сторінка» в таблиці —
прочерком. Розбивати документ на псевдо-сторінки по N рядків **не будемо**:
поріг був би довільним, а помилка дорого коштує саме тут — на боці хибного
звинувачення.

### 3.5 Модуль `parser/text_forensics.py`

```python
@dataclass
class HomoglyphHit:
    word: str                  # як у документі
    restored: str              # як мало би бути
    rule: Literal["mixed", "lone"]
    severity: Severity
    page: int | None
    line_index: int

@dataclass
class ForensicsResult:
    hits: list[HomoglyphHit]
    total_words: int
    affected_pct: float
    pages_affected: list[int]          # завжди порожній для DOCX
    likely_encoding_issue: bool

def scan_text_forensics(lines: list[LineItem]) -> ForensicsResult:
```

Сканується **весь** документ, включно з бібліографією: підміна в списку
літератури ламає пошук самих джерел.

**Невидимі символи (`U+200B`, `U+200C`, `U+200D`, `U+00AD`, `U+FEFF`,
`U+2060`) у цей етап не входять** — вони переїжджають у `ROADMAP.md`. План
рахував їх у полі `invisible`, але ніде не показував, тобто робота йшла в
нікуди. Пункт вилучається цілком: поле, підрахунок і тест. Ніщо інше в етапі 3
від нього не залежало.

### 3.6 Відображення

Секція «🔤 Підміна символів» у вкладці «Асистент антиплагіату», **без кнопки**:
скан по 12 тис. рядків укладається в частки секунди, а результат кешується
через `@st.cache_data` по `lines_to_tuple(lines)`.

* метрики: уражених слів · % тексту · сторінок (остання — тільки для PDF);
* `st.error` із поясненням, коли `likely_encoding_issue` — щоб експерт не
  зробив висновок про підміну там, де винен конвертер;
* таблиця: `Сторінка` · `У документі` · `Мало бути` · `Правило`; для DOCX
  колонка «Сторінка» — прочерк, як уже зроблено в «Абзацах без посилань»;
* рядок номерів сторінок через наявний `format_number_ranges()` — для PDF.

### 3.7 Тести — `tests/test_text_forensics.py`

Чисті функції над рядками, PyMuPDF не потрібен. Усі сім кейсів із 3.3
переносяться в тести дослівно — вони вже написані як пари «вхід → очікування».
Додатково:

* верхній регістр `РОЗДIЛ` (латинська `I`) знаходиться;
* `ї` ↔ `ï` знаходиться;
* H2 для `y`/`o`/`a`/`e` **мовчить**, поки H1 дало менше 3 знахідок,

* `x` не спрацьовує ніколи;
* рівномірна підміна по всіх сторінках → `likely_encoding_issue = True`;
* точкова підміна на двох сторінках із десяти → `likely_encoding_issue = False`;
* **DOCX-режим** (`page = None` в усіх рядках): рівномірна підміна > 5 % слів
  → `likely_encoding_issue = True`, `pages_affected == []`;
* **DOCX-режим**, точкова підміна < 5 % слів → `likely_encoding_issue = False`;
* порожній документ не падає (`total_words == 0`, ділення на нуль).

## Що лишається за межами етапу

За рішенням експерта: онлайн-верифікація існування джерел (Crossref, OpenAlex,
DOI), контрольні цифри ISBN/ISSN, суцільні блоки сиріт, цитати в лапках без

ризику, експорт звіту. Опис усіх цих перевірок лишається в `ROADMAP.md` —
файл не переписуємо, щоб не втратити обґрунтування на випадок повернення
до них.

Додатково винесено за межі етапу під час узгодження плану:

| Пункт | Куди | Чому |
|---|---|---|
| Невидимі символи (`U+200B` тощо) | ROADMAP | рахувались, але не показувались; вилучено цілком (§3.5) |
| Гомогліфи у зворотний бік (кирилиця в латиниці) | ROADMAP | англомовна анотація — 2–3 сторінки проти двохсот (§3.2) |
